# scripts

Repo-level scripts that are not shipped. Plain bash, because they predate the Bun workspace.

| Script | What it does |
|---|---|
| `verify-staging.sh` | Read-only. Runs checks V1 to V15 (LLD 0 section 2.1) and exits 0 only if all pass. Prints reasons for each failure, never a secret value. |
| `provision-staging.sh` | Idempotent. Creates what the checks assert, one step at a time. `apikey` restricts the public Firebase web API key to the services the client calls (V15); it is a no-op once the restriction is in place. `channel` creates the `dc-owner` email notification channel that every policy in `ops/alerts/` names; it is a no-op once the channel exists, and without one it needs `ALERT_EMAIL`, supplied at run time and never committed. The address travels to `curl` on stdin, so it never reaches an argv or the output. |
| `wait-indexes.ts` | Bun. `bun scripts/wait-indexes.ts --project <id> [--timeout-min 30]`. Polls every 30 s until every composite index is `READY` and the TTL field config on `expiresAt` for the six collection groups is `ACTIVE`, then exits 0 (since #32 that is four composites, LLD 3 section 4). A `CREATING` state is retried; `NEEDS_REPAIR`, a missing field config, a non-zero `gcloud` exit or the timeout fails at once, naming the offender. Exit 2 on bad arguments. It reads Firestore through `gcloud` only (ADC). Tested by `wait-indexes.test.ts`, whose fake `gcloud` lives in `fixtures/fake-gcloud.sh`. |
| `ops-apply.ts` | Bun. `bun scripts/ops-apply.ts --project <id> [--channel-name dc-owner]`. Applies the declaration in `ops/` (LLD 0 section 9): 20 log-based metrics (`ops/metrics/*.yaml`), the `dc main` dashboard (`ops/dashboards/main.json`) and 20 alert policies (`ops/alerts/*.json`). Creates what is absent and updates what is present, so a second run creates nothing; then it re-lists everything and fails, naming any declared item the project does not have (P20). It resolves the notification channel by display name over the Monitoring REST API and refuses to run without it, pointing at `provision-staging.sh channel`. Rendered configs go to a temp directory outside the repo (`verify` runs `git diff --exit-code`). Prints counts only, never a credential: the access token comes from `gcloud auth print-access-token` and stays in memory. Exit 0 applied and verified, 1 a declaration, the channel or an item is missing, 2 usage. Tested by `ops-apply.test.ts`: the tree itself (OB1 to OB4), injected effects (OB5 to OB9) and a real child process against the fake `gcloud` plus a local Monitoring server (OB10). `MONITORING_API_URL` is the only override and is refused unless it names a loopback host, so a stray value in a credentialed job cannot redirect the bearer token; it exists for that test. The access token comes from `gcloud auth print-access-token`, falling back to `gcloud auth application-default print-access-token` for the Workload Identity Federation path the deploy uses. |
| `smoke.ts` | Bun. `bun scripts/smoke.ts --project <id>`. Post-deploy checks against the real project: `ping` returns `ok` on Node 22 with an App Check token, and the same call without a token is rejected (`unauthenticated`/`failed-precondition`), which is what proves enforcement. The App Check token comes from `APPCHECK_DEBUG_TOKEN` when set (CI); otherwise one is minted, registered and deleted in the same run. The debug token is exchanged for an App Check JWT first (`:exchangeDebugToken`) because the callables verify a real JWT. It then runs every query declared in `functions/src/store/queries.ts` (`limit 1`, Firestore REST `runQuery`, the access token from `gcloud` as in `ops-apply.ts`): `FAILED_PRECONDITION` (a missing or building index) fails naming the query, and `PERMISSION_DENIED` fails separately, naming the likely missing role on the caller rather than an index (#32). Prints outcome lines only and redacts every value it sent from any error it reports, so no token reaches stdout or stderr. Exit 0 pass, 1 fail, 2 usage. Custom-token sign-in is not covered here: the probe moved to the identity step (LLD 4 section 13). Tested by `smoke.test.ts` with injected effects (S1, S2 for the queries). |
| `check-web-size.ts` | Bun. `bun scripts/check-web-size.ts [dist]` (default `apps/web/dist`, so run `bun run build:web` first). Fails if gzip sizes exceed LLD 7 section 10.1: entry 300 KB, lazy chunk 60 KB, CSS 20 KB, service worker 40 KB (a KB is 1000 bytes). Tested by `check-web-size.test.ts`, which also holds `web-build.test.ts` (builds per mode, the no-referrer meta tag, the App Check debug-token guard); both run in `bun run test`. |
| `scan-secrets.ts` | Bun. `bun scripts/scan-secrets.ts` (from the repo root). The P13 secret scan: the pinned betterleaks 1.10.1 over the source tree only (`git ls-files --cached --others --exclude-standard`, so gitignored build output is never scanned), with `.betterleaks.toml`, findings redacted. Exit 0 clean, 1 findings, 2 wrong or missing binary (`BETTERLEAKS_BIN` overrides the path). Tested by `scan-secrets.test.ts` against the real binary in throwaway git repositories (a planted fake key fails it). |
| `install-betterleaks.sh` | `bash scripts/install-betterleaks.sh <dest-dir>`. Installs betterleaks 1.10.1 after verifying the release asset's sha256 against the pinned value (linux x64/arm64, macOS x64/arm64); a mismatch installs nothing and exits 1. Idempotent. CI puts `<dest-dir>` on `PATH`; locally `brew install betterleaks` also works. |
| `check-bundle-no-bun.sh` | `bash scripts/check-bundle-no-bun.sh [functions-dir]` after `bun run build:functions` (P7). Loads `functions/dist/index.cjs` with `node` under a minimal `PATH` (`CLEAN_PATH`, default `/usr/bin:/bin`) and fails if the bundle does not load or if `bun` is still reachable on that `PATH`. |
| `log-sentinels.ts`, `run-integration-sentinels.ts` | The P19 log-sentinel harness. `bun run test:integration:logs` runs `test:integration`, keeps everything the emulators print plus `firebase-debug.log`, and fails if a planted sentinel (`NAME-SENTINEL-*`, `CARD-SENTINEL-*`, `sentinel@example.test`) appears; it reports file and line, never the line. `functions/test-integration/sentinels.test.ts` plants them in an accepted and a rejected `ping`. `bun scripts/log-sentinels.ts <file>...` scans any log. |
| `seed.ts` | Bun. `bun scripts/seed.ts --fixture <name>` or `--all` builds the emulator fixture catalogue (LLD 3 section 10.1, #37) through the real `createGame`/`runCommand` on the Node Functions bundle. Refuses a `GCLOUD_PROJECT` without the `demo-` prefix, a missing `FIRESTORE_EMULATOR_HOST`, an unknown fixture and a malformed argument (exit 2; a refusal exits 1, success 0). Every fixture has a fixed 20-character game id and per-command idempotency keys, so a second run replays with zero writes. Prints ids and counts only. `--all` is the nine-fixture CI catalogue and runs inside `test:integration`; `midsize10` (the size fixture, about 60 s) is opt-in with `--fixture midsize10`. Tested by `scripts/seed.test.ts` (pure argv and env checks) and `functions/test-integration/store/fixtures.test.ts` / `fixtures-size.test.ts` (the emulator build). |
| `skills.ts`, `skills.test.ts` | Bun. The skill layout AGENTS.md documents: every `.agents/skills/<name>` has a `SKILL.md` whose frontmatter `name` matches its directory, `.claude/skills/<name>` is a symlink to it, AGENTS.md's table lists exactly those names, and every relative `../<skill>/...` reference in a skill resolves. `checkSkills` returns coded violations (`SK01`–`REF01`). Part of `bun run test`; S5 to S9 plant each kind of breakage and prove the code, so a green run says the plumbing is intact. What a skill's prose makes an agent do is not asserted here: the pilot run proves that. |
| `rules-coverage.test.ts`, `firestore-indexes.test.ts` | Part of `bun run test`. P10 (#32): every collection `firestore.rules`, LLD 3 section 2.1 and tech-stack section 5 name is exercised by the rules matrix (`rules-test/matrix.ts`), and the three lists agree; LLD 3 section 3.1 is `firestore.rules` verbatim. The indexes test asserts `firestore.indexes.json` is LLD 3 section 4: four composites, 17 exemptions, six TTL overrides. |
| `ci-policy.test.ts` | Asserts LLD 0 section 8 over `.github/workflows/ci.yml` (triggers, `DEPLOY_REF`, permissions, pinned actions, deploy flags and order, preview and fork safety, the debug token, verify, emulator, prod stub, concurrency). Part of `bun run test`. Validate syntax with `actionlint` (1.7.12; `brew install actionlint`; `.github/actionlint.yaml` ignores the deliberate `if: false` on `deploy-prod`). |

## Prerequisites

`gcloud` (logged in, `gcloud auth login`), `firebase` (`firebase login`), `gh` (logged in with `repo` and admin scope on the repository), `jq`, `curl`, `openssl`, `betterleaks`, `actionlint` (to lint the workflow). Pinned at setup: `firebase-tools` 15.37.0, Google Cloud CLI 594.0.0, betterleaks 1.10.1.

## Running

```sh
scripts/verify-staging.sh                                   # all 15 checks
BILLING_ACCOUNT=XXXXXX-XXXXXX-XXXXXX scripts/provision-staging.sh all   # `all` skips `channel` (see below)
ALERT_EMAIL=<address> scripts/provision-staging.sh channel # the dc-owner notification channel, once
scripts/provision-staging.sh apikey                         # restrict the public web API key (V15)
scripts/provision-staging.sh iam wif                        # or any subset of steps
```

`all` logs `channel` as skipped when `ALERT_EMAIL` is unset, so the documented one-liner still works on a fresh project; an explicit `channel` run fails and says what to set.

Steps, in dependency order: `project firebase apis firestore iam wif secrets webapp auth appcheck config apikey channel`. Each is safe to re-run. `BILLING_ACCOUNT` is needed only by `project` and `ALERT_EMAIL` only by `channel`; both are supplied at run time and never committed. Budget alerts email the billing account's admins.

## Notes

- Nothing needs the console. The only human decision is which billing account to use.
- The six TTL policies are declared in `firestore.indexes.json`, not created by `provision-staging.sh`: `firebase deploy --only firestore` applies them (proven in #15). A new or re-enabled policy shows `CREATING` for a few minutes before `ACTIVE`; `wait-indexes.ts` and V4 fail until then.
- The deploy order is LLD 0 P16: `firebase deploy --only firestore`, `wait-indexes.ts`, functions, hosting, `ops-apply.ts`, `smoke.ts`. `ops-apply.ts` joined that order in #17 (P20): `deploy-staging` runs it on every push to `main`, so a project missing a declared metric, the dashboard, a policy or the `dc-owner` channel fails the deploy rather than drifting.
- 2nd gen functions build as the default compute service account, whose `roles/editor` is removed (V8). It needs `roles/storage.objectViewer`, `roles/artifactregistry.writer` and `roles/logging.logWriter` for the build; without them `firebase deploy --only functions` fails in Cloud Build with "missing permission on the build service account" (found in #15).
- The first functions deploy in a region asks for an Artifact Registry cleanup policy; `bunx firebase functions:artifacts:setpolicy --project <id> --location <region>` sets it (1 day) and keeps later deploys exiting 0 (found in #15).
- New projects take a minute or two before IAM is consistent; if a command fails with `USER_PROJECT_DENIED`, retry.
- Secret values (three Secret Manager secrets, the App Check debug token) are generated and piped over stdin; they are never printed, passed as command-line arguments, written to disk or committed. Rotating one means creating a new secret version by hand.
- Public client config (Firebase web config, reCAPTCHA site key) is committed in `apps/web/.env.staging`; `.betterleaks.toml` allowlists exactly that path. The web API key is public by design, so the `apikey` step restricts it to the six services the client calls (V15) rather than treating it as a secret. No HTTP-referrer restriction: `smoke.ts` exchanges the App Check debug token server-side with no `Referer`. The update can be refused with `APIKEYS_RESTRICTION_INCOMPATIBLE_WITH_USAGE` when the public key has recent traffic for a service being removed (usually 403 probes); inspect the usage in Cloud Monitoring and, if it is only probing, set `APIKEY_SKIP_USAGE_CHECK=1` for that run.
